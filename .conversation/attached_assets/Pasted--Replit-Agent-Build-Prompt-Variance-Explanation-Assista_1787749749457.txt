## Required pipeline — implement in this exact order, and do not let any stage skip ahead of the one before it

### 1. Structured input form (NOT a chatbox)
- On `index.html`, show an editable **table/grid**, not free text input.
- Columns: `Category` (text), `Forecast` (number), `Actual` (number), `Notes` (optional text).
- Start with 3 empty rows visible; include an "Add Row" button (simple vanilla JS to append a row) and a "Remove Row" button per row.
- A single "Analyze Variances" submit button posts all rows to the backend at once.

### 2. Input validation (runs on the backend, before anything else)
Validate every submitted row and reject the whole submission with clear, specific error messages if:
- `Category` is empty or whitespace only
- `Forecast` or `Actual` is missing or not a valid number
- `Forecast` is negative (0 is allowed, negative is not)
If validation fails, re-render the form with the user's entered values still filled in, plus a red error banner listing exactly which rows/fields failed and why. Do not proceed to any later stage if validation fails.

### 3. Logic layer — plain Python, NO AI involved (put this entirely in `logic.py`)
For each valid row, compute:
- `variance = actual - forecast`
- `variance_pct = (variance / forecast) * 100` — handle `forecast == 0` safely (avoid divide-by-zero; if forecast is 0, set variance_pct to `None` and note it's undefined)
Then:
- Rank all rows by **absolute value** of `variance` (largest first), and select the **top 3 to 5** as "key drivers" (5 if there are 5+ rows, otherwise however many rows exist, minimum 1).
- Apply **rule-based pre-classification** using simple keyword matching (case-insensitive) on the `Notes` field for each key driver, in this priority order:
  1. If notes contain "price" or "rate" → tag = `"price driver"`
  2. Else if notes contain "delay", "pushed", or "early" → tag = `"timing driver"`
  3. Else if notes field is empty/blank AND `abs(variance_pct)` is large (use a threshold of 25% — define this as a named constant so I can tune it later) → tag = `"anomaly"`
  4. Else → tag = `"volume driver"` (default)
Write this as a pure function, e.g. `compute_key_drivers(rows) -> list[dict]`, with no side effects and no network/API calls, so it's easy to test on its own.

### 4. Prompt construction (in `ai_client.py`)
Build a function `build_prompt(key_drivers)` that constructs a prompt sending **only** the computed key driver data to the LLM — never the raw full row list, and never anything not already computed in Stage 3. For each key driver include: `category`, `variance_pct`, `rule_based_tag`, `notes`.
The prompt must explicitly instruct the model:
- "Only use the numbers and tags provided below. Do not invent causes, root causes, or business context not supported by this data. If the data is insufficient to explain a driver with confidence, say so explicitly in the explanation and lower the confidence score accordingly."
Request the response as **JSON only**, with this exact schema, one object per key driver, returned as a JSON array:
```json
[
  {
    "driver_category": "string, matching the category name given",
    "classification": "one of: volume, price, timing, anomaly",
    "explanation": "one sentence, plain English",
    "confidence": 0
  }
]
```

### 5. Real LLM API call
Call the OpenAI API using model `gpt-4o-mini`, sending the constructed prompt. Use the OpenAI Python SDK (`pip install openai`). Set `response_format` to enforce JSON output if the SDK version supports it; otherwise instruct strongly via the prompt and parse defensively (see Stage 6). Wrap the call in a `try/except` — if the API call fails (timeout, auth error, rate limit, network issue), catch it and return a clear error object rather than crashing the app.

### 6. Output parsing
Parse the returned JSON safely:
- Strip markdown code fences (```json ... ```) if the model wraps its output in them.
- Use `json.loads` inside a `try/except`.
- If parsing fails, or the response is missing expected fields, or `classification` isn't one of the four allowed values, or `confidence` isn't a number 0–100 — do NOT crash. Instead, build a fallback object for that driver: `classification: "unknown"`, `explanation: "AI response could not be parsed — please review this driver manually."`, `confidence: 0`.

### 7. Confidence/flag check
For each parsed driver result:
- If `confidence < 60`, set a flag: `low_confidence = True`.
- If `classification` (from AI) does not match `rule_based_tag` (from Stage 3, ignoring the word "driver" — e.g. "price driver" vs "price"), set a flag: `tag_mismatch = True`.
Both flags should be visually shown in the UI in Stage 9, they are not mutually exclusive.

### 8. Database persistence (in `database.py`, SQLite)
On app startup, create the database file and a table (if it doesn't already exist) with columns to store, per submission:
- `id` (primary key, autoincrement)
- `timestamp`
- `raw_input` (JSON string of all submitted rows)
- `computed_drivers` (JSON string of Stage 3 output)
- `ai_output` (JSON string of Stage 6/7 parsed + flagged output)
- `avg_confidence` (float, computed across that submission's drivers)
- `low_confidence_flag` (boolean — true if ANY driver in this submission had confidence < 60)
Write clear functions: `init_db()`, `save_submission(...)`, `get_all_submissions()`, `get_submission_by_id(id)`.

### 9. Structured UI output (`results.html`)
Display results as readable **cards**, one per key driver — never show raw JSON to the user. Each card shows:
- Driver/category name
- Variance % (formatted, e.g. "+18.4%" or "−9.2%", with color: green for favorable, red for unfavorable — you decide the convention and note it in a comment)
- A color-coded classification badge (e.g. blue=volume, orange=price, purple=timing, red=anomaly)
- The one-sentence explanation
- A confidence bar or percentage, visually distinct (e.g. a horizontal bar filled proportionally)
- If `low_confidence` is true: a clearly visible "⚠️ Low confidence — verify manually" badge
- If `tag_mismatch` is true: a clearly visible "⚠️ AI classification differs from rule-based tag" badge, showing both tags

### 10. Admin dashboard (`/admin` route, `admin.html`)
- List all past submissions in a table: timestamp, number of drivers, avg confidence, whether it had a low-confidence flag, with a link/button to view that submission's full results again.
- Show one aggregate stat at the top: "**X% of reports have at least one low-confidence driver**" computed from all submissions in the database.
- Handle the empty-database state gracefully (e.g. "No reports yet — submit your first variance analysis" instead of a blank/broken table).

## Error handling requirements (apply throughout, not just Stage 6)
